To really explain all of these different methods that work well, I think you need to really only understand one core idea to start with, and then we're going to elaborate and build upon that idea. And that idea to start with is the associativity of multiplication. So let's think about how attention works. We can write it in this compact notation, where we say, the attention operation is going to be of Q, Ks, and Vs, with these matrix dimensions up here. And I'm going to take my Qs and the Ks, and I'm going to have an all to all interaction. All the n positions are going to interact with each other by matrix multiplication. And then I'll normalize them through a softmax, this row over here. And then I will multiply it with my values V to get the attention outputs. This is a classic self-attention or whatever other attention operation. Now, for the moment, let's forget that attention has a softmax. And then I'm just going to drop the row. Forget it for the moment. Now, if we didn't have a row, maybe we can actually change the complexity of this operation. So if you look at attention, it's n squared dk, because we're taking this QK transpose multiplication. But if Rho was the identity, I can just move the parentheses around a little bit. And I can say, all right, instead of QK transpose V, really, what I'm going to have is QK transpose V. And if we do this reordering, well, we've changed which part is quadratic. Instead of having the n squareds, which were pretty terrible, because these n's are very big. They're millions. It's the context length. Instead, I can have dependence on ndvdk. So now, we're multiplying essentially, the key and the value dimensions. These could be big, in principle. I can have a big model. But these are usually on the order of thousands, tens of thousands. And so this is a much more favorable term to be dependent on compared to this n squared term when we were doing this original attention operation. 要真正解释所有这些不同的有效方法，我认为你一开始只需要理解一个核心思想，然后我们会在这个思想基础上进行阐述和构建。这个核心思想就是乘法的结合性(associativity of multiplication)。让我们想想注意力是如何工作的。我们可以用这个简洁的符号来写：注意力操作涉及 Q、K 和 V，矩阵维度如上所示。我把 Q 和 K 拿来，进行全对全的交互。所有 n 个位置通过矩阵乘法相互交互。然后我通过一个 softmax（这一行）对它们进行归一化。然后我把它与值 V 相乘，得到注意力输出。这是经典的自注意力(self-attention)或任何其他注意力操作。现在，暂且让我们忘记注意力有 softmax。我把这一行去掉，暂时忘了它。如果我们没有这一行，也许我们实际上可以改变这个操作的复杂度。如果你看注意力，它是 n的平方 乘以 dk，因为我们做了 QK 转置的乘法。但如果 Rho 是恒等映射，我可以稍微移动一下括号。我可以说，好的，与其做 QK转置 乘 V，不如我做 Q 乘 (K转置乘 V)。如果我们做这个重排，我们就改变了哪一部分是二次的。我们不再有 n的平方——这非常糟糕，因为这些 n 非常大，是百万级别的，就是上下文长度。相反，我可以依赖 n 乘以 dv 再乘以 dk。所以现在，我们本质上是在乘键(key)和值(value)的维度。原则上，这些可能很大。我可以有一个大模型。但这些通常是在几千、几万的数量级。没有人在隐藏维度中拥有百万个坐标。所以这是一个比我们做原始注意力操作时的 n平方 项要有利得多的依赖项。所以这是你应该知道的第一件事：乘法的结合性允许我们改变对序列长度的依赖。

Now, the other thing that we can do now is, if we consider this reordering, this QK transpose V, something that's even nicer about this, and I think this has led to really, a lot of the research that I'm going to mention in the next couple of slides, is that this matrix multiply on the right, in the self-attention case, looks just like an RNN. Well, RNNs are quite nice, because at inference time, I have this S, which is my state, it's fixed in size. And I'm just carrying that forward and forward. So RNNs are very nice for inference reasons. They are not nice for training reasons. But nice thing about linear attention is, you can use them in either way. 现在，我们还能做的另一件事是：如果我们考虑这种重排——这种 Q(K转置V)——还有一个更好的性质，我认为这实际上促成了我将在接下来几张幻灯片中提到的很多研究，那就是在自注意力的情况下，右边的矩阵乘法看起来就像一个 RNN。我不需要用上面的密集形式来写，我可以增量地写。当我在上下文上从左到右扫描时，我可以乘 K 和 V，更新这个叫做 S 的东西（一个状态），并把它加到我的前一个状态上。这是对 KV 的增量乘法和累加。然后我可以用 Q 乘以它来得到输出。上面的密集操作和这个 RNN 形式是等价的。那么我们做了什么呢？我们从左上角的线性注意力开始，然后不知何故得到了一个看起来非常像 RNN 的东西。RNN 有什么好处呢？RNN 非常好，因为在推理时，我有这个 S，它是我的状态，大小是固定的。我只需要把它不断向前传递。所以 RNN 在推理方面非常好。它们在训练方面不太好。但线性注意力的好处是，你可以以任何一种方式使用它们。你可以用这种密集形式——这对训练很好，它是并行的。或者你可以用这种序列形式，像 RNN 一样——这对推理很好。所以你可以两全其美。至少就所有这些对象的依赖性而言，这很好，这很棒。不幸的是，这是线性的，不是很好。这确实是我们讨论的起点。

I want some more serious complex neural network stuff to be happening. Well, what you can now do is-- oh, sorry, I went a little too far, look at the RNN form of linear attention. And we can add a small elaboration to linear attention in order to get more expressive updates. And this is how you end up getting Mamba-2. Some of you may have heard of Mamba, Mamba-2, Mamba-3 now, I think. These are a family of state space models by Albert Gu, and Tri Dao, and friends. And they're derived, originally, from this state space theory and view. But actually, if you look at the mechanics of what is being done, you can actually see it as a very simple elaboration of the linear attention mechanism. And so the idea is the following. So we start with linear attention. And you might say, really, the main problem with linear attention is that I'm always passing my state forward. We know, from the olden days of LSTMs, that it's important to when to pass information forward and when to just not pass information forward, to forget things and send them to 0. So what I'm going to do is, I'm going to be inspired by that. And I'm going to add a gate, gamma of t. Gamma of t is not stateful. Gamma of t only depends on my current inputs x of t. And gamma of t is going to modulate how much of my state I'm going to carry forward into the future. Now, if you think about this, the state-dependent terms are all these Ss. This gamma is not state-dependent at all, so this means that this is very simple to compute. And there's still this duality. You can compute this Mamba-2 term, either as a big dense matrix multiply or at inference time, use it in this recurrent form to get nice inference improvements. So that's the core conceit or view of this idea that you can either use it in parallel or sequence, just like linear attention.

现在我们讲完了线性注意力。但你可能会说，线性注意力太幼稚太简单了，这不是我想要的。我想要更严肃、更复杂的神经网络东西发生。那么你现在可以做的是——哦，抱歉，我走得太远了——看看线性注意力的 RNN 形式。我把线性注意力的等式写在这里，这样你就不用来回翻了。我们可以对线性注意力添加一个小小的扩充，以获得更有表达力的更新。这就是你最终得到 Mamba-2 的方式。有些人可能听说过 Mamba、Mamba-2，现在还有 Mamba-3。这一系列状态空间模型(state space models)由 Albert Gu、Tri Dao 及其合作者提出。它们最初来源于这种状态空间理论和视角。但实际上，如果你看它的运作机制，你实际上可以把它看作是线性注意力机制的一个非常简单的扩充。所以思路如下：我们从线性注意力开始。你可能会说，线性注意力的主要问题是我总是把我的状态向前传递。我们从早期 LSTM 的时代就知道，何时向前传递信息、何时不向前传递信息、忘记一些东西并将其置零，这很重要。所以我受此启发，要添加一个门控(gate)，记作 gamma_t。gamma_t 是无状态的，它只依赖于我当前的输入 x_t。gamma_t 将调节我携带多少状态进入未来。如果你考虑一下，状态相关的项都是这些 S。这个 gamma 完全不依赖于状态，所以这意味着计算起来非常简单。而且仍然存在这种对偶性(duality)。你可以以两种方式计算这个 Mamba-2 项：要么作为一个大的密集矩阵乘法，要么在推理时使用这种循环形式(recurrent form)来获得很好的推理改进。这就是这个思想的核心——你可以像线性注意力一样，以并行或序列的方式使用它。

You can take your one data set and split it up over many machines. You can do model parallelism, where you can take your model, and maybe you can split up your model over different machines. For data parallelism, you're maxed out your batch size. Once you hit your batch size, you can't parallelize by data anymore. For model size, there's natural cut points, where you can cut your model. Once you exhaust those, you can't parallelize anymore. If you combine this with expert parallelism, you get another additional nice access to parallelize on. And when you do this, a lot of the underlying implementations for this allow you to take advantage of sparse matrix multiply that has been built into GPUs.

酷。好的。现在在结束之前，我想谈一点系统方面的事情。训练 MoE 引入了额外的有趣的系统动态。当我谈论并行化时，我主要会谈论标准的——我们称之为——并行化形式。你可以把你的数据分成很多小块。你可以把你的一个数据集分割到多台机器上。你可以做模型并行化(model parallelism)，你可以把你的模型分割到不同的机器上。你可以以各种方式结合这两者——当然你可以那样做。但我认为我们意识到的是，每种并行化技术都有一些限制。对于数据并行化(data parallelism)，你用尽了你的批大小(batch size)。一旦你达到批大小，你就不能再通过数据来并行化了。对于模型大小，有自然的切分点，你可以在那里切分你的模型。一旦你用尽了这些，就不能再并行化了。如果你把这与专家并行化(expert parallelism)结合起来，你就得到了另一个额外的好维度来进行并行化。当你这样做时，很多底层实现允许你利用已经内置于 GPU 中的稀疏矩阵乘法(sparse matrix multiply)。

So another thing that I'll mention is, if you have multiple experts, let's say, on one GPU, one way of thinking about it is to say, I'm going to have multiple small matrix multiplies. But this is not nice, because you ideally want these bigger matrix multiplies, where you can reuse caches and do all sorts of things. So instead, what you can do is, you can nicely leverage sparsity. And block diagonal, of course, is the most basic form, but you can use much more of complicated forms of structured sparsity that are natively supported in hardware to allow you to essentially multiply experts and inputs in very, very clean ways, very fast. So this is another reason why MoEs are nice. If you think about the computation patterns of MoEs, they almost correspond to these kinds of structured matrix multiplications that are very easy and efficient to support in hardware. So there's this hardware architecture codesign that's happening with MoEs.

另一个我要提到的是，如果你有多个专家，比如在一个 GPU 上，一种思考方式是：我会做多个小矩阵乘法。但这不好，因为你理想上想要这些更大的矩阵乘法，在那里你可以重用缓存并做各种事情。所以相反，你可以很好地利用稀疏性。块对角(block diagonal)当然是最基本的形式，但你可以使用更复杂的结构稀疏性(structured sparsity)形式——这些在硬件中原生支持——让你基本上以非常非常干净的方式、非常快地乘专家和输入。所以这是 MoE 好的另一个原因。如果你考虑 MoE 的计算模式，它们几乎对应于这些结构化的矩阵乘法，非常容易和高效地在硬件中支持。所以 MoE 存在着这种硬件架构协同设计(hardware architecture codesign)。

And in terms of parallelism, one thing I'll mention, this is a very recent development. This is from Nemotron-3. I forgot who asked this question. When we do this expert parallelism, we have to be shipping activations from device to device in order to say like, oh, you belong in that expert, I need to ship you over. That can result in significant communications overhead. So some of the things that people have started to think about is to say, well, my shared expert, which I'm not going to communicate, this can be in big dimensions. But my experts, I need to communicate those activations, I want those to be in smaller lower dimensional vectors. So you might actually take your residual stream and downproject it first, and then decide to do the collective communication call of sending this activation out. And that will significantly save on communication without fully having the drawbacks of having a smaller hidden dimension size. So you can actually do these kind of projection tricks to nicely control the trade-off of communication and having your MoEs parallelized.

在并行化方面，我要提到一件事，这是一个非常近期的进展。来自 Nemotron-3。我忘了谁问了这个问题的。当我们做这种专家并行化时，我们必须把激活从设备传输到设备——"哦，你属于那个专家，我需要把你送过去。"这可能导致显著的通信开销。所以人们开始思考的一些事情是：我的共享专家——我不需要通信的——这可以是大维度的。但我的专家——我需要通信那些激活——我希望它们是更小的低维向量。所以你可能实际上拿你的残差流，先降维投影它，然后决定做发送这个激活的集合通信调用。这将在没有完全承受更小隐藏维度大小的缺点的同时，显著节省通信。所以你可以做这种投影技巧来很好地控制通信和 MoE 并行化之间的权衡。

One final trivia, let's call it detail of MoEs that I think is fun, but it has been solved in recent years, is stochasticity. If you do MoE infrastructure naively, what you'll find is that, unless your experts are perfectly balanced on your input distribution, you'll find that certain experts might be much more popular than others. And if some expert like, let's say, in this case, expert 0 is just a really popular expert, you're going to actually start running into situations where this expert queue of tokens just starts building up, and building up, and building up. And eventually, you'll get to a point, where you say, my queue is so long, I have to start dropping tokens. And the earlier generation of MoE inference infrastructure and code, a lot of what happened was, you would just actually silently drop this expert. And you just proceed on with your computation as if nothing had happened. You just send a zero back and pretend that that was fine. And this means that you can have these weird stochasticities, where if other users sent in queries that hit the experts that you're using, then you could actually get a worse result, because they would bump you out of the expert queue. These kinds of very strange things can happen. But these days, they drop less architectures that have gotten rid of a lot of these issues. So this is no longer really an issue. So mega blocks and other very common open source MoE frameworks don't have this issue anymore.

最后一个趣闻——我们称之为 MoE 的细节——我认为很有趣，但在最近几年已经被解决——是随机性(stochasticity)问题。如果你天真地做 MoE 基础设施，你会发现，除非你的专家在你的输入分布上是完美平衡的，你会发现某些专家可能比其他的更受欢迎。如果某个专家——比如在这个例子中，专家 0 是一个真正受欢迎的专家——你实际上会开始遇到这种情况：这个专家队列中的标记开始堆积、堆积、堆积。最终，你会到达一个点，你说："我的队列太长了，我必须开始丢弃标记。"在早期一代的 MoE 推理基础设施和代码中，很多情况下，你会实际上静默地丢弃这个专家。你继续你的计算，好像什么都没发生。你只是送回一个零，假装那没问题。这意味着你可能会有这些奇怪的随机性：如果其他用户发送的查询命中了你在使用的专家，那么你实际上可能得到一个更差的结果，因为他们会把你挤出专家队列。这类非常奇怪的事情可能发生。但如今，那些消除了很多这些问题的架构丢弃得更少了。所以这已经不是真正的问题了。MegaBlocks 和其他非常常见的开源 MoE 框架不再有这个问题。

So the last thing that I'll talk about in terms of the design of MoEs is this issue of stability. We've already talked about stability issues in the context of architecture design last lecture. OK. The last MoE-specific trick that I'll mention is this idea of upcycling. This has actually become a lot less popular in the last year. I don't think I've seen a single upcycled model this year. So upcycling is this idea that if you want a MoE, maybe you can just take a dense model that you've trained, and then you can instantiate a MoE based on that dense model. And the idea is, you just copy everything, including the MLPs. You just make a whole bunch of copies from these MLPs. You have a router, which have a random initialization. And then you just train this model. And if you do this, then because of the stochasticity of which inputs go to where and the MLP, you're going to get these experts that start to specialize. And in the end, you'll actually end up with MoE. And in some of the earliest papers that proposed upcycling, they show that an upcycled method could get much better language modeling, in this case, accuracy, performance, upcycling a dense model rather than continuing to train the same model, which is a cool thing that you can show. People have validated this at scale in many ways. So many CPM is another Chinese model that I quite like, because they do a lot of carefully controlled ablations. They had a MoE, where they took their miniCPM 2.4b model. They upcycled it to a 13.4 billion parameter model. And they got a bunch of almost free wins from doing that.

好的。我要提到的最后一个 MoE 特定技巧是上循环(upcycling)的概念。这实际上在过去一年中变得不那么流行了。我认为今年我没见过一个上循环的模型。但这是一个很酷的想法。而且早期有一些非常棒的模型使用了这个技巧。所以我想提一下。上循环是这样的想法：如果你想要一个 MoE，也许你可以直接拿一个你训练好的密集模型，然后基于那个密集模型实例化一个 MoE。思路是：你复制所有东西，包括 MLP。你从这些 MLP 中制作一大堆副本。你有一个随机初始化的路由器。然后你训练这个模型。如果你这样做，那么由于输入去哪里和 MLP 的随机性，你会得到这些开始专业化的专家。最终，你会实际得到一个 MoE。在一些最早提出上循环的论文中，他们展示了上循环方法可以获得更好的语言建模——在这种情况下是准确性和性能——将密集模型上循环而不是继续训练同一个模型，这是一个你可以展示的酷东西。人们在各种方式下在大规模上验证了这一点。Mini CPM 是另一个我非常喜欢的中国模型，因为他们做了很多仔细控制的消融实验。他们有一个 MoE，他们拿了他们的 miniCPM 2.4B 模型，上循环到一个 134 亿参数模型，并且从中获得了几乎免费的收益。

The only complexity that you might need to worry about is that this is going to conflict with rope when you do KB caching.
