## GPU vs. CPU: Philosophical Differences / GPU 与 CPU：哲学层面的差异

So how is the GPU different from a CPU? Those that have interacted with the GPU already know this. We'll move on to more advanced things in a minute. But for the rest of you, I think it's very important to understand the model, the philosophy in some sense, of how they're different. So a CPU is designed for quick, serial execution where you have complex branching logic, complex conditionals, complex control flows. Because of this, a CPU, generally speaking, has really big control units. And it has a few ALUs that can do mathematical or other operations. But this is meant to run very quickly. So you want to go as fast as possible and have low latency. The time between when you get an instruction and when you complete it should be very, very short. That's the general CPU design philosophy.

GPU 与 CPU 有什么不同？那些已经接触过 GPU 的人已经知道这一点，我们很快会进入更高级的内容。但对于其余同学，我认为理解它们的模型，从某种意义上理解它们不同的"哲学"，非常重要。CPU 是为快速串行执行而设计的，你需要处理复杂的分支逻辑、复杂的条件判断、复杂的控制流。因此，一般来说，CPU 有非常大的控制单元，有少量 ALU 可以执行数学或其他运算。但这一切都是为了运行得非常快。你希望尽可能快，并且具有低延迟。从获取指令到完成指令之间的时间应该非常非常短。这就是 CPU 设计的总体哲学。

In contrast, the GPU is really about throughput. The plot on the right, I think, is a great pictorial illustration of, when you change these philosophies, what you end up getting. So in a GPU, maybe you dispatch a task, it takes a long time for it to finish. It might be that you process a task, and then you stop, and then you go work on another task, and then you go back and work on another task. But in general, even though your tasks don't finish quickly, you're getting large aggregate throughput across all of your tasks. And what enables this is having tons and tons of lightweight cores. So a GPU has hundreds and hundreds of compute units that are packed into a chip. And all of these can execute in parallel. So this is a very different mode of programming and thinking compared to a CPU.

相比之下，GPU 的核心是吞吐量。右边的图很好地展示了当你改变这些设计哲学时，最终会得到什么结果。在 GPU 中，你派发一个任务，它可能需要很长时间才能完成。你可能处理一个任务，然后暂停，去做另一个任务，然后再回来处理另一个任务。但总的来说，即使你的任务没有很快完成，你在所有任务上获得了巨大的聚合吞吐量。使这成为可能的是大量的轻量级核心。GPU 在一个芯片上集成了成百上千个计算单元，所有这些都可以并行执行。所以这与 CPU 的编程和思维模式非常不同。

## GPU Hardware Model / GPU 硬件模型

And I want to demystify what a GPU is. I don't want you to think of it as a set of pieces of text on NVIDIA-SMI. I want you to be able to visualize what the hardware is of a GPU. I think this picture is usually used as a pictorial illustration of what a GPU is. I think this is a great logical picture of what's happening inside of a GPU. So a GPU, the basic unit of a GPU is SM, a streaming multiprocessor. And a streaming multiprocessor is kind of a core. It's its own independent compute unit that has subcomponents that it can use to accelerate its computation. And it has access to certain kinds of memories that it can connect to. So each SM, building on this idea of parallelism, it's not a single compute unit. It has streaming processors inside of it that can then execute different threads in parallel. But an SM is the discrete compute unit. Each SM, you can think of as a core, almost. And GPUs have tons of SMs. An A100 will have 128 SMs. Each of these can be independently programmed, and they can independently execute different jobs. And they have access to global memory outside of it.

我想揭开 GPU 的神秘面纱。我不希望你把它想成 nvidia-smi 上的一串文字，我希望你能直观地想象 GPU 硬件是什么。我认为这通常被用作 GPU 的图示说明。这是一张非常棒的逻辑图片，展示了 GPU 内部发生的事情。GPU 的基本单元是 SM，即流式多处理器（streaming multiprocessor）。流式多处理器可以看作是一个内核，是一个独立的计算单元，拥有可用于加速计算的子组件，并且可以访问某些类型的存储器。基于并行性的思想，每个 SM 不是一个单一的计算单元，它内部有流式处理器（streaming processor），可以并行执行不同的线程（thread）。但 SM 是离散的计算单元，你几乎可以把它看作一个核心。GPU 有大量的 SM。A100 有 128 个 SM，每一个都可以独立编程，独立执行不同的任务，并且可以访问外部的全局内存（global memory）。

And the other thing that we will see—that's the compute story of a GPU. But we will see throughout this lecture that a really, really important part of this story is not just the compute part but the memory part. Modern hardware and LLM optimization is really defined by the memory. And so we need to understand what the memories are and where they live. So when we talk about memory, there's different kinds. There's different levels of caches that are connected to a GPU. There are registers, which are even more limited and even faster. And then you have global or high-bandwidth memory. And as you can see from this table—this is a benchmarking that some folks did, I think this was at A100 latencies—the L1 and shared memory, these are very fast. In something like 20 to 30 cycles you can read and get data from them. If you're hitting the L2 cache, much slower, and if you're hitting global memory, that's 10 times slower than the L1 cache. This is a big difference in your speed.

我们还会看到另一件事——以上是 GPU 的计算故事。但在整个讲座中，我们会发现这个故事中极其重要的一部分不仅仅是计算部分，还有内存部分。现代硬件和 LLM 优化实际上是由内存定义的。所以我们需要了解有哪些内存以及它们在哪里。当我们谈论内存时，有不同种类。有连接到 GPU 的不同级别的缓存。有寄存器（register），它们更有限但更快。然后有全局内存或高带宽内存。正如你从这张表中看到的——这是有人在 A100 上做的延迟基准测试——L1 和共享内存（shared memory）非常快，大约 20 到 30 个周期就能读取和获取数据。如果命中 L2 缓存，速度慢得多；如果命中全局内存，比 L1 缓存慢 10 倍。这是速度上的一个巨大差异。

And this global memory is kind of what you normally think of as a high-level programmer as GPU memory. When H200 tells you I've got 144 gigs of memory, you're talking about global memory. You're not talking about shared or L1 cache. Now, physically, where do these things live? Well, global memory usually are these kind of memory chips that live outside of your compute unit, whereas L2 and L1 cache, they kind of live physically in the chip itself. So this is the picture of a GPU chip. And you see all of these SMs. These green blocks are SMs. And you see L2 right here. And the L1 is inside of each of these SMs. So they're physically much closer to the compute units. That's why their latency is so much better.

全局内存通常是高级程序员所认为的 GPU 内存。当 H200 告诉你有 144GB 内存时，你谈论的是全局内存，而不是共享内存或 L1 缓存。那么从物理上讲，这些东西在哪里？全局内存通常是位于计算单元外部的内存芯片，而 L2 和 L1 缓存在物理上位于芯片内部。这就是 GPU 芯片的图片。你看到所有这些 SM——这些绿色块就是 SM。你看到 L2 就在这里。而 L1 在每个 SM 的内部。所以它们在物理上离计算单元更近，这就是为什么它们的延迟要好得多。

And you might say, OK, then if shared memory is so nice, why don't you build a whole chip out of shared memory? It's much more expensive, hundreds of times. It's also much more power hungry from the way that these memories are built. And so this is the reason why if you're building a practical accelerator, often you don't want to just have a giant amount of shared memory. You want to have this hierarchy of memory and use it effectively. I think Grok, which was recently acquired by NVIDIA, was a design where you just have these giant amounts of SRAM. And for certain workloads like inference, this is very helpful. But still, for most accelerators, you're going to have this hierarchy that you're going to really have to respect in order to make anything run fast.

你可能会说：好吧，如果共享内存这么好，为什么不把整个芯片都用共享内存来做？它要贵得多，几百倍。从这些内存的构建方式来看，它们也更耗电。这就是为什么如果你在构建实用的加速器，通常你不想只有大量共享内存，你想要这种内存层级结构并有效利用它。我认为最近被 NVIDIA 收购的 Grok 是一种设计，你有大量的 SRAM。对于像推理这样的某些工作负载，这非常有帮助。但对于大多数加速器来说，你都会有这种层级结构，你必须尊重它才能让任何东西跑得快。

So the shared memory and the L1 cache operate differently. The cache is really just a cache thing that is storing recently accessed data elements. Shared memory is a programmable element that you'll actually interact with, that you can put things in and out of. So that's the memory story. And keep that in mind because it's going to keep coming back, the memory hierarchy. That's a really important object.

共享内存和 L1 缓存的工作方式不同。缓存真的只是一个缓存，存储最近访问的数据元素。共享内存是一个可编程的元素，你会实际与之交互，可以往里面放东西和取东西。所以这就是内存的故事。请记住这一点，因为内存层级结构会不断回来——这是一个非常重要的对象。

## GPU Programming Model / GPU 编程模型

Now, we have the hardware mental model in place. And now we're going to start talking about the software and programming model of a GPU. So there's three different important players that live in the execution model of a GPU. So there's a thread. And if you're familiar with multiparallel programming of any kind, you know what a thread is. A thread is a lightweight thing that's running in parallel and doing some work. In a GPU, an important thing about the threads is they follow the SIMT model, which means that all of the threads that you have are executing the same exact instructions. They're going to have different inputs, which means that the threads can actually do separate useful work, but the instructions they execute have to all be the same. And this has important implications for both the efficiency of your code as well as the programming model. If the threads can do all sorts of different stuff, it becomes very hard to program. GPUs are this tradeoff between programmability and efficiency.

现在我们已经建立了硬件心智模型，接下来开始讨论 GPU 的软件和编程模型。在 GPU 的执行模型中有三个重要的参与者。首先是线程（thread）。如果你熟悉任何形式的多并行编程，你知道线程是什么。线程是并行运行并做一些工作的轻量级实体。在 GPU 中，线程的一个重要特性是它们遵循 SIMT（单指令多线程）模型，这意味着你所有的线程都在执行完全相同的指令。它们有不同的输入，这意味着线程实际上可以做不同的有用工作，但它们执行的指令必须全部相同。这对代码的效率和编程模型都有重要影响。如果线程可以做各种不同的事情，编程就会变得非常困难。GPU 是程序可编程性和效率之间的这种权衡。

Now, a block is a group of threads. And the reason why a block is a relevant object is that a block is guaranteed to run on a single SM. And remember, an SM has a shared memory. And so you can think of a thread as doing work in parallel. Blocks have access to a shared pool of memory. That will become very important later when we talk about this idea called tiling, where these blocks are going to be reusing the same pieces of memory. Finally, a warp is essentially the scheduling unit of what is happening inside the GPU. Threads are going to execute in groups of 32 consecutively numbered threads. That is a warp. This decreases the overhead of a scheduler deciding which threads to run. But essentially, these are the important three terminology items for GPU. I might say something like, oh, we're going to have different warps executing. That's what I mean here. That's a basic unit of 32 threads that execute together.

接下来，线程块（thread block）是一组线程。线程块之所以重要，是因为一个线程块保证在单个 SM 上运行。记住，一个 SM 拥有共享内存。所以你可以将线程想象为并行工作，而线程块可以访问共享内存池。这在后面讲分块（tiling）概念时会变得非常重要——这些线程块将重复使用相同的内存片段。最后，线程束（warp）本质上是 GPU 内部的调度单元。线程以 32 个连续编号线程为一组来执行，这就是一个线程束。这减少了调度器决定哪些线程运行的开销。总的来说，这三个是 GPU 最重要的术语。我可能会说"我们将有不同的线程束在执行"，这就是我的意思——一个由 32 个线程组成的、一起执行的基本单元。

## GPU Memory Model / GPU 内存模型

And so in the memory model of a GPU, device code can read from registers. Registers are some of the fastest and most local items. This might be storing things like memory addresses of where you might need your arrays start and end. That's a place where you might store things in registers. Then you've got local memory. This is local, too, within your single SM. You've got shared memory that can be accessed within your block. So if you have something you want to transfer across threads or you want to have information that is going to be reused across threads, those are going to live in shared memory. You can, of course, then read from global memory, the DRAM that's far away, as long as you're willing to pay the latency hit of waiting for data to come to you from global memory. And there's also constant memory, which I don't think I've seen very much used in various programming things, that you can use as well. Now, you can even transfer to and back from host memory. When I say host memory, that means CPU memory that lives on the machine. You can do this if you need to offload beyond the size of your GPU.

在 GPU 内存模型中，设备代码可以从寄存器（register）读取。寄存器是最快、最局部的存储单元之一，可以存储诸如数组起始和结束位置的内存地址等内容。然后是局部内存（local memory），它也在单个 SM 内部。你有共享内存（shared memory），可以在线程块内访问。所以如果你有需要在线程之间传递的东西，或者有需要在线程间复用的信息，它们将驻留在共享内存中。当然，你也可以从全局内存（global memory）——也就是远处的 DRAM——读取数据，只要你愿意承担等待数据从全局内存传过来的延迟代价。还有常量内存（constant memory），我觉得在各种编程场景中不太常见。你甚至可以在主机内存（host memory）和 GPU 之间传输数据。主机内存指的是机器上的 CPU 内存。如果需要在超出 GPU 大小的情况下卸载数据，可以这样做。

And really, the key thing, the most important part of this memory model, is that as soon as you go outside of your shared memory, things are going to be slow. So grouping the blocks to decrease the amount of global memory reads is going to be the name of the game throughout this lecture.

这个内存模型最关键、最重要的部分是：一旦你走出共享内存，事情就会变慢。所以通过分组线程块来减少全局内存读取次数，将是贯穿整个讲座的核心主题。

TPU 和 GPU 之间的核心思维差异是：TPU 在某种意义上更简单。它们更针对机器学习工作负载优化。它们有轻量级的控制单元，有更大的矩阵乘法单元。它们具有与 GPU 相同的基本结构：有专门的电路来做矩阵乘法，有可以做并行向量操作的组件，有某种控制系统。它们有非常相似的内存结构：有慢速内存（称为高带宽内存），还有更快的局部内存（称为 SMEM 或共享内存）。所以这与 GPU 的架构看起来非常非常相似。真正的区别在于这些东西的大小以及操作的灵活性。

如果你看一个 GPU，像 A100 这样的典型 GPU 可能有大约 132 个流式多处理器。这是很多处理器。而一个 TPU 只有两个单元，只有两个独立的单元在并行运行。如果我们只看矩阵乘法单元，GPU 有 528 个矩阵乘法单元，而 TPU 只有 8 个。这些大致上是可以比较的规模。为什么会这样？TPU 依赖数量少但更大的矩阵乘法单元，而 GPU 依赖数量多但更小的矩阵乘法单元。你可以想象，如果你有很多矩阵乘法单元，会有更多灵活性，可以给它们编程做这做那。而在 TPU 上，你被锁定在大规模矩阵乘法上。

### Trick 1: Control Divergence / 技巧一：控制分歧

The first one is a GPU-specific thing. And it relates to one of the things I said before, the SIMT model. So in a GPU, every thread is executing the same thing. Now, what happens if you write an If statement on a piece of code that executes on a GPU? On a CPU, it's quite clear what happens. On a CPU, you will either pick one branch or the other, you will execute that branch. And you will move on with your life. In a GPU, you will do something actually quite different and slightly counterintuitive. Every thread has to execute the same instruction. So actually, every thread will execute both the If and the Else. But if you're not part of the If branch, you will just mask out that computation. You'll just sit idle.

第一个是 GPU 特有的，与之前讲过的 SIMT 模型有关。在 GPU 中，每个线程执行相同的指令。现在，如果你在一个在 GPU 上执行的代码中写一个 if 语句会怎样？在 CPU 上，很清楚会怎样——你会选择其中一个分支执行，然后继续。在 GPU 上，实际上会做完全不同且有点反直觉的事情。每个线程必须执行相同的指令，所以实际上每个线程将执行 if 和 else 两个分支。但如果你不属于 if 分支，你只会掩蔽掉那个计算，只是闲置等待。

So whenever you have a conditional, your mental model for the execution kind of looks like this. Part of your threads will diverge based on this If statement. Some of them will go to the bottom branch, some of them will go to the top branch. And the bottom branch ones will execute first, top branch ones will wait. And then the top branch ones will execute, and the bottom branch ones will wait. So in order to execute an If statement, you're actually walking through both of these. And then some of the threads are just waiting, doing nothing if they're on the wrong side of the branch. And this is called control divergence. And this is nice in some ways because it simplifies programming. It's not nice in that you now have these big compute gaps where your GPU is doing nothing. This is one of the reasons why you really do not want to write If statements. If you look at GPU code, if you have a ReLU, you'll often find you're multiplying with zeros or multiplying with masks instead of doing an If statement where you're updating half, because a multiplication is going to all go at once. And an If statement might actually have to wait two clock cycles or something like this, two operations.

所以每当有一个条件分支，你的执行心智模型看起来像这样：部分线程会基于这个 if 语句发生分歧（diverge）。一些去底部分支，一些去顶部分支。底部分支的线程先执行，顶部分支的线程等待。然后顶部分支的线程执行，底部分支的线程等待。所以为了执行一个 if 语句，你实际上是在走过两条分支。然后如果线程在错误的分支一侧，它们就只是等待，什么都不做。这叫做控制分歧（control divergence）。这在某些方面是好的，因为简化了编程。但不好的地方在于，你现在有这些巨大的计算空白，你的 GPU 什么都没做。这就是为什么你真的不想写 if 语句的原因之一。如果你看 GPU 代码，一个 ReLU 通常会乘以零或乘以掩码，而不是用 if 语句来更新一半的值——因为乘法是一次性全部执行的，而 if 语句可能实际上需要等待两个时钟周期。

### Trick 2: Low Precision / 技巧二：低精度

The first one, which you don't really have to do too much for, but I think is one of the most important ones, and hardware-wise, I think where NVIDIA is investing the most effort, is low-precision computation. And if you look at this plot—I've brought Bill Dally back to the slide—this super exponential growth, where does this really come from? Actually, a pretty nontrivial part of this is number representations. You start at FP32, you go to BF16, and then you go to Int8. You just keep decreasing the precision of your numbers. And of course, if you have half the bits, you have half the bits to move. And so you have your memory movement. And so you've solved the memory bottleneck for at least a little bit.

下一个技巧你不需要做太多事情，但我认为是最重要的技巧之一，而且从硬件角度看，我认为 NVIDIA 投入最多精力的领域，就是低精度（low precision）计算。如果你看这张图——我又把 Bill Dally 放回到幻灯片——这个超指数级增长，它到底从何而来？实际上，一个相当重要的部分来自数字表示。你从 FP32 开始，到 BF16，再到 Int8。你一直在降低数字的精度。当然，如果位数减半，需要移动的位数也减半，所以内存移动也减半。就这样，你至少在某种程度上解决了内存瓶颈。

This is a dumb example. But I'm just going to really drill it in there. Let's say, I have a ReLU on a vector of size n. If I'm on float 32, I need to do one read to read my number. I need to do one write after I've computed my ReLU. That's going to be 4 bytes per operation, total of 8 bytes for my memory access. I only have one FLOP worth of operation. So that's 8 bytes for FLOP. If I have half the precision, of course, I've halved the number of bytes per op. I've halved the number of bytes that I need to move per FLOP.

这是一个简单的例子，但我要确实讲透。假设我对大小为 n 的向量做 ReLU。如果用 float32，我需要做一次读取，计算完 ReLU 后做一次写入。每次操作 4 字节，总共 8 字节内存访问。我只有一个 FLOP 的操作量。所以每个 FLOP 需要 8 字节。如果精度减半，每个操作的字节数当然也减半，每个 FLOP 需要移动的字节数也减半。

Now, that's a very simple example. But actually, how low precision works in a modern GPU is actually very complicated and actually either very cool or very crazy, depending on how you think about how cool things are. So when you do a matrix multiply, let's say, you have a tensor core that's operating in lower precision, how does that actually work in practice? Well, you're actually not going to keep everything in low precision. You're going to downcast before you take your product. And when you sum up your partial summands in your matrix multiply, you're going to do this in full precision. And then you might emit your outputs or your results in FP32.

这是一个非常简单的例子。但实际上，低精度在现代 GPU 中如何工作是非常复杂的，要么很酷要么很疯狂，取决于你怎么看待。当你做矩阵乘法时，假设你有一个在低精度下运行的张量核心，实际是怎么工作的？你实际上不会把所有东西都保持在低精度。你会在做乘积之前向下转换（downcast）。在矩阵乘法中累加部分和时，你会用全精度来做。然后你可能以 FP32 格式输出你的结果。

And part of, I think, the reason why low precision is actually kind of a black art is not because you can just decrease precision. Anyone can do that. You have to figure out which of your operations has to be in which number format. So matrix multiplies, maybe both your weights and activations can be low precision. If I'm doing a softmax, maybe I need to do that in FP32. Or if I'm doing an exponential, maybe that also needs to be FP32. Or maybe I can get away with BF16. So I think it took several years, really, to get low-precision training to be the state that it is today. And a lot of that work was slow, incremental, empirical work figuring out which of these operations we can downcast, how we can downcast them, and how we can preserve stability of training while making as much of our training and inference low precision as possible.

我认为低精度之所以是一种"黑色艺术"，不是因为你可以简单地降低精度——任何人都可以这样做——而是你必须弄清楚哪些操作需要用什么数字格式。矩阵乘法，可能权重和激活都可以是低精度的。如果做 softmax，可能需要在 FP32 中做。如果做指数运算，可能也需要 FP32。或者也许可以用 BF16 搞定。我认为真正花了几年时间才让低精度训练达到今天的状态。大量工作是缓慢、渐进、经验性的，弄清楚哪些操作我们可以降精度，如何降精度，以及如何在尽可能让训练和推理变为低精度的同时保持训练的稳定性。

People have been pushing this further and further. I think once you think about how hard it is to pay for fast memory, you realize, if only I can cut my precision by another factor of 2. People really, really want to do that. And so FP8 was the next frontier, I would say, of low precision. Once you get to FP8, there's no longer a standard, canonical format that everyone uses. If you're using 16 bits, you're probably using BF16 for a lot of what you're doing. But with FP8, there's going to be E4M3, which stands for four bits of exponent and three of mantissa. Or there's going to be E5M2, which is more exponent, fewer mantissa. Because these are used in different places, there's no one-size-fits-all once you start to get to so few bits.

人们一直在进一步推动这个极限。一旦你意识到快速内存有多贵，你就会想：如果能把精度再降低 2 倍该多好。人们非常非常想这样做。FP8 是低精度的下一个前沿。一旦到了 FP8，就没有一个标准、规范的格式了。如果你用 16 位，你可能大量使用 BF16。但到了 FP8，有 E4M3——4 位指数和 3 位尾数。还有 E5M2——更多指数位、更少尾数位。因为它们用于不同的地方，当位数这么少时，没有万能的格式。

But I think the thing that's really interesting is the more advanced, low-precision number formats that are coming out with the new hardware. So I'll talk briefly about MXFP8 because it's both cool and what it does to training is strange, to say the least. So in FP8, the traditional version of training, what you have is that all of, let's say, activations are in 8 bits. And then you're going to have a scaling factor in FP32 that's going to allow you to scale this up and down. Why do you have a scaling factor? The scaling factor is necessary because you only have four bits of exponent, let's say. That's so few bits of exponent you're going to quickly over or underflow. So you need the scaling factor to keep you in the right range so you can keep some information.

但我认为真正有趣的是随着新硬件推出的更高级的低精度数字格式。我简单谈谈 MXFP8，因为它既酷，对训练的影响也至少可以说很奇怪。在 FP8 的传统训练版本中，假设所有激活值是 8 位。然后你有一个 FP32 的缩放因子（scaling factor），让你可以上下缩放。为什么需要缩放因子？缩放因子是必需的，因为比如你只有 4 位指数，这么少的指数位你会很快溢出或下溢。所以你需要缩放因子来保持你在正确的范围内，以便保留一些信息。

Well, people realized this is not optimal because a single matrix might have very different magnitudes. One part of my sequence might have much bigger activations than another. So instead of having a single scaling factor, why don't we have many scaling factors? So MXFP8 and these multiscale factor formats that are much more advanced now have many scaling factors. Each of these scaling factors corresponds to the relevant colored submatrix. So the first four elements in this matrix correspond to this first scaling factor and so on and so forth. Now I have more scaling factors, these scaling factors are actually going to be in lower precision. These are going to be 8 bits as well. They're going to be E8M0. So they only have exponent bits. So they're all powers of 2 in 8 bits. So you have to make these tradeoffs.

人们意识到这不是最优的，因为单个矩阵可能有非常不同的量级。序列的一部分可能比另一部分有大得多的激活值。所以与其只有一个缩放因子，为什么不有很多缩放因子呢？MXFP8 和这些更高级的多缩放因子格式现在有很多缩放因子。每个缩放因子对应相关的有色子矩阵。第一个缩放因子对应矩阵的前四个元素，依此类推。现在有更多缩放因子，而这些缩放因子实际上也将是低精度的——也是 8 位，是 E8M0 格式。所以它们只有指数位，都是 8 位中 2 的幂。你必须做这些权衡。

So MXFP8 is going to use more mantissa in the elements. Scale factors are themselves FPA. And you're going to have one scale factor every 32 elements in your matrix. Now, think for a moment. What is the problem with this design? What is the big issue if you do something as clever as this? So the big issue here is—let's say, I want to transpose this matrix. The transpose of this matrix does not have the same pattern, so to speak, scaling pattern as this matrix. And so now it used to be that a transpose of a matrix was simple. I just transpose this matrix. I don't have to requantize. I don't have to do anything. Transposing this matrix is very complicated because I now have to potentially requantize this whole matrix to fit this 1 out of 32 pattern that I have. And so what happens internally when you actually use MXFP8—and I found this to be crazy but also kind of cool—is that when you're training your model with this thing, it actually creates two copies of every quantized matrix, one for your original matrix, one for the transpose. So if you ever want to transpose, you have the transposed version waiting for you. And that's how you get around this.

所以 MXFP8 在元素中使用了更多尾数。缩放因子本身是 FPA。你的矩阵中每 32 个元素有一个缩放因子。现在，想一想。这个设计有什么问题？做这么聪明的事情，最大的问题是什么？最大的问题是——假设我要对这个矩阵做转置。这个矩阵的转置不具有相同的缩放模式。过去，矩阵转置很简单：我只是转置这个矩阵，不需要重新量化（requantize）。转置这个矩阵变得非常复杂，因为我现在可能需要重新量化整个矩阵以适应每 32 个元素一个缩放因子的模式。所以当你实际使用 MXFP8 时内部发生的事情——我发觉这又疯狂又有点酷——就是在用这个训练模型时，它实际上为每个量化矩阵创建了两份副本：一份是原始矩阵，一份是转置矩阵。所以如果你想做转置，你已经有了转置版本在等着你。这就是你解决这个问题的方法。

The point here is maybe not to emphasize the GPU trivia. But the point here is that once you start getting to these FPA, FP4 formats, things start getting pretty exotic because the amount of exponent and mantissa loss that you have are pretty extreme. So you have to be very clever about how you do this. This plot does show what I was saying. So every time you quantize, you're going to quantize one way, and you're going to transpose and quantize. So you're going to have both copies. And then the other part, which I told you about a few slides ago, is you're only going to quantize certain layers that you think are safe to do so. And this is another trial and error thing that you have to figure out. But once you have all this together, you have the big benefits of training in FP4, which is that when you're doing those matrix multiplies, you're probably going to get 20% to 30% savings, maybe more, depending on the size of your matrix. Unfortunately, it's not going to be a 2x speedup because you have to do all these quantization operations. There's a big overhead doing this. So it's not free.

这里想强调的不是 GPU 冷知识，而是一旦你开始进入 FPA、FP4 这些格式，事情变得相当奇特，因为指数和尾数的损失是非常极端的。所以你必须在处理方法上非常聪明。这张图确实展示了我说的：每次量化时，你以一种方式量化，然后又转置并量化，所以你会有两份副本。另一部分是，你只量化那些你认为安全的层——这是另一个需要试错解决的问题。但一旦你掌握了所有这些，你就得到了 FP4 训练的显著好处：在做那些矩阵乘法时，可能会节省 20% 到 30%，甚至更多，取决于矩阵大小。不幸的是，不会是 2 倍的加速，因为你必须做所有这些量化操作，有巨大的开销。所以不是免费的。

The next frontier, this is already implemented as MXFP4. The entirety of MXFP8 can be shown to you in this slide. It's negative 6 to 6. You have all the possible values. But now that you understand MXFP8, you can also understand how this thing works. You're going to have a structured block, where each block is going to be one of these four bits. Every 16 of these numbers, you're going to have one scaling factor. And that scaling factor will itself be FP8, a E4M3 scaling for those scaling factors. There has been a paper that has trained with FP4. I don't think I've heard of anyone successfully training in the wild, real, big, serious models with FP4. But I think this is coming. The next generation of models will probably be FP4. So that was low precision. I think it's really cool that you can really push the limits so far that you're ending up with just plus 6 to negative 6, and yet you can do interesting things with matrices in that precision.

下一个前沿已经实现为 MXFP4。MXFP8 的全部值可以在这张幻灯片上展示：从 -6 到 6 的所有可能值。但现在你理解了 MXFP8，也就能理解 MXFP4 如何工作了。你会有一个结构化的块，每个块是 4 位。每 16 个这样的数字会有一个缩放因子，而这个缩放因子本身是 FP8，对这些缩放因子使用 E4M3 格式。已经有论文用 FP4 进行训练了。我没听说过有人在真实的大规模、严肃模型上成功用 FP4 训练，但我认为这正在到来。下一代模型可能就是 FP4。所以这就是低精度。我认为非常酷的是，你可以把极限推到只是从 +6 到 -6，却仍能在那个精度下用矩阵做有趣的事情。

### Trick 3: Operator Fusion / 技巧三：算子融合

So the other trick—this one is much more of a conceptual programming thing—is operator fusion. It's a fairly simple idea. But you'll be surprised at how much this doesn't already happen. So think of a GPU as a factory. You've got your memory warehouse. And you've got your little compute factory. And you've got a little belt conveyor going back and forth. If you scale up your compute, you're going to be bottlenecked by your little belt conveyor. And this will be worse if you have many operations. Imagine I've got lots of different operations I need to do. And I'm going to ship my raw materials to my factory and back and forth and back and forth. This is a lot of memory bottleneck that you're paying for and lots of duplex bidirectional memory bandwidth. Now, wouldn't it be better if I just had one giant factory that would take all the raw materials and ship back my finished product? This way, I only have to pay for memory bandwidth twice, very simple idea. This is operator fusion.

下一个技巧更多是一个概念性编程的东西——算子融合（operator fusion）。想法相当简单，但你会惊讶于这在实践中常常没有被做到。把 GPU 想象成一个工厂。你有你的内存仓库，有你的小计算工厂，还有一条小传送带来回运输。如果你扩大计算能力，你会被那条小传送带所瓶颈。如果你有很多操作，这会更糟糕。想象我有许多不同的操作需要做。我要把原材料运到工厂，来回反复。这是你在为之付出代价的大量内存瓶颈，以及大量的双向内存带宽。如果我只用一个巨大的工厂，把所有的原材料拿进去，然后把我的成品运回来，不是更好吗？这样我只用付出两次内存带宽的代价。想法很简单。这就是算子融合。

And this appears very often. If you write a very simple, let's say, computation of sine squared plus cosine squared, what does the PyTorch computation graph look like? It looks like this. You got your x, I do my sine, I do my cosine. I square it on both sides, I add them. And I get my output. Naively, if you don't do anything smart, what this will do is each of these will be a factory, so to speak. You will read and write from global memory each time one of these is called. And you will incur quite a bit of memory cost every time you do so. So this is pretty painful.

这经常出现。如果你写一个非常简单的计算，比如 sin^2 + cos^2，PyTorch 的计算图是什么样子？看起来像这样：你有 x，做 sine，做 cosine，分别平方，然后相加得到输出。朴素地看，如果你不做任何聪明的事，每一个操作都会像一个工厂。每次调用其中一个，你都会从全局内存读写，每次都产生相当多的内存成本。这相当痛苦。

And you can imagine instead of doing that, why don't I just write GPU code that reads once from global memory, does the whole thing inside the SM, as I talked about before. And then after it's done inside the SM, I'm going to write it back to global memory, a single kernel that does all of these operations. This is called fusion. And anything that's easy like this—this is a very easy fusion. It's like a graph that I can just squish down into a single unit—a compiler can automatically do this for you. So Torch compiler, which is a compiler for PyTorch, or JAX compiler, which is JAX's compiler, which is more deeply integrated into JAX, both of these will fuse these kinds of basic things into a single CUDA call.

你可以想象，与其这样做，不如直接写 GPU 代码，只从全局内存读取一次，在 SM 内完成整个计算，然后在 SM 内完成后，写回全局内存——一个单一的 kernel 完成所有操作。这就是融合。像这种容易的情况——非常容易的融合，就像一个图可以压缩成一个单元——编译器可以自动帮你做。所以 Torch compiler（PyTorch 的编译器）或 JAX compiler（深度集成到 JAX 中的编译器），都会把这类基本操作融合成单个 CUDA 调用。

### Trick 4: Recomputation / 技巧四：重计算

The third idea is recomputation. So we know in back propagation, what do we do? We go forwards upwards on the tree. You go upwards on the tree. And you keep track of activations. You store these little activation numbers. And then when I go backwards, I'm going to use the activations that I stored to compute the backward signal down my tree. We all know backprop to some extent. But also, now we're looking at this not from the perspective of mathematics, how do we compute a gradient. We're thinking about this from the perspective of systems. How do we minimize our memory?

下一个想法是重计算（recomputation）。我们知道在反向传播中，我们向前向上走过计算树，跟踪激活值，存储这些激活数值。然后在向后走时，用存储的激活值来计算向下的反向信号。我们在某种程度上都理解反向传播。但现在我们不是从数学的角度来看——如何计算梯度——而是从系统的角度来看：如何最小化内存？

Well, if we think about what's happening, let's say, I have something simple: I have x sigmoid, sigmoid, sigmoid out. Each of these sigmoids is going to generate in the computation graph some residual or some activation that I need to track. So after my first operation, I have S2, second operation, S1. And then when I need to do my backwards pass it will consume S2, S1, and my output, or sorry, the gradient at my output. And I'm going to push this backwards towards the derivative of my input. So if I count the number of memory reads and writes, it's going to be one memory read for x, three memory writes for S2, S1, out. And then on the backwards pass, this is flipped. So this is a total of eight memory reads and writes, very low arithmetic intensity because I'm just stacking a bunch of sigmoids.

考虑这个简单情况：x -> sigmoid -> sigmoid -> sigmoid -> out。每个 sigmoid 在计算图中会产生一些需要追踪的残差或激活值。在第一个操作后，有 S2；第二个操作后，有 S1。然后做反向传播时，它消费 S2、S1 和输出的梯度，向后推到输入的导数。如果数一下内存读写次数：x 一次读取，S2、S1、out 三次写入。反向传播时反过来。总共八次内存读写，算术强度非常低，因为只是堆叠了一堆 sigmoid。

Now, what can I do instead? Well, what I can do is, I can just throw away all of the activations. Normally, you wouldn't do this. Why would I want to recompute something? But imagine you're in a world where computation is super, super cheap. You just have abundant computation. You're not using all of your units. But your memory is very expensive. Any read and write has a lot of penalty. Then you might prefer this computation graph where I read an x, and then I'm going to do sigmoid, sigmoid, sigmoid, output. I'm going to store this output. I have to write this because that's the output of my graph. But now in the backwards pass, my backwards graph is going to get in d_out. And on the fly, I'm going to reforward the x and then compute the activations on the fly right where I need them. So now this is going to be two memory reads for the d_out and dx and one memory write for the dx. So I've gone from eight total memory accesses to just five. So now I have 5/8 the total memory accesses, same computation. But I've spent a little bit of extra compute and saved a little bit of extra memory. This is another very important trick. We don't normally think about this because, usually, we're concerned with just computing the gradient. But once you have a systems mindset, you start to think about recomputation.

那我可以怎么做？我可以直接扔掉所有激活值。通常你不会这样做——为什么要重计算？但想象在一个计算超级超级便宜的世界里，你有充足的计算能力，没有用完所有单元，但内存非常昂贵，任何读写都有很大惩罚。那你可能更倾向于这种计算图：读取 x，做 sigmoid -> sigmoid -> sigmoid -> out。存储 output——必须写因为它是我图的输出。但在反向传播中，我的反向图获取 d_out，然后即时重新前向传播 x，在前向计算激活值，正好在需要它们的地方。所以现在是：两次内存读（d_out 和 dx），一次内存写（dx）。从总共八次内存访问减到五次。所以只有 5/8 的内存访问，同样的计算量。多花了少量额外计算，节省了少量额外内存。这是另一个非常重要的技巧。我们通常不会这样想，因为通常我们只关心计算梯度。但一旦有了系统思维，你会开始考虑重计算。

### Trick 5: Memory Coalescing / 技巧五：内存合并

Trick number four. This is another memory trivia thing but surprisingly becomes important and also why sometimes it's important to understand the hardware model of what you're interacting with. So global memory, which is the big memory that lives outside the chip, is DRAM. And DRAM, because of the way that it is structured, actually comes in bursts. What that means is, when I access, let's say, the very first position, I don't actually get just the first value. I can read off all four of these first values for free. And that's because the way the memory cells are lined up, there's these blocks of memory units. And then when I activate an amplifier, I can just read out all of these almost for free. The way that it's structured in parallel allows me to read blocks of memory. That makes sense as a hardware model. And so this is called a burst section. And so whenever a section is accessed, all the other locations can also get delivered for free. And you won't pay for them, so to speak.

这是另一个内存冷知识，但出人意料地重要，也解释了为什么有时理解你所交互的硬件模型很重要。全局内存，即芯片外部的大内存，是 DRAM。DRAM 由于其结构方式，实际上是以 burst 方式工作的。这意味着当我访问第一个位置时，我实际获得的不仅仅是第一个值。我可以免费读取这四个连续的值。这是因为内存单元的排列方式——有这些内存单元块——当我激活一个放大器时，几乎可以免费读出所有这些值。它并行结构的方式允许我读取内存块。这种硬件模型是有道理的。这叫做 burst 段。每当一个段被访问时，所有其他位置也可以免费获取。

And so you might have something like 128 bytes worth of a burst. That means a single read will return, potentially, 128 bytes worth of data, as long as it lives in the same contiguous block. So this means that if you have your reads arranged contiguously where they're all together, it's going to go much faster. And to use a term, you say that a memory access is coalesced. So that word means if all of the threads in a warp fall in the same burst. So what that means is, let's say, I have three threads, sorry, four threads. And my four threads live inside of a single burst section, or they're reading from this burst section. Then this is coalesced because they're using up all of this entire burst section. And I'm fully utilizing this very nice property of DRAM memory. And so if I have multiple warps, I'm going to have different multiple burst sections. But you can efficiently read out of memory by grouping together your memory reads.

你可能有大约 128 字节的 burst。这意味着单次读取可能返回多达 128 字节的数据，只要它们位于同一个连续块中。所以如果你的读取是连续排列的，它们在一起，速度会快得多。用一个术语来说，这种内存访问叫做合并（coalesced）。这个词的意思是：一个线程束中所有线程的访问落在同一个 burst 内。比如有四个线程，它们都在一个 burst 段内或者从这个 burst 段读取。这就是合并的，因为它们正在利用整个 burst 段。你完全利用了这个非常好的 DRAM 内存特性。如果有多个线程束，你会有多个不同的 burst 段。但通过将内存读取分组在一起，你可以高效地从内存中读出数据。

So why am I telling you DRAM trivia? The reason why I'm telling you DRAM trivia is because—think about matrices. Matrices, you often want to read in big blocks because you're going to do matmuls. And certain kinds of memory accesses on matmuls are privileged. They're much more nicely structured than others. And sometimes you can take advantage of this to get very, very fast memory reads. So the mnemonic or the thing that I remember is, if you have threads and you have a row major matrix, so it's sorted where each row is how your indexes are increasing, threads that move along the major axis are not coalesced.

我为什么告诉你 DRAM 冷知识？原因在于——想想矩阵。矩阵，你经常想按大块读取，因为你要做矩阵乘法。在矩阵乘法中，某些类型的内存访问是特权化的，它们比其他访问在结构上更优越。有时你可以利用这一点来获得非常非常快的内存读取。我记住的口诀是：如果你有线程和一个行主序矩阵（按行增加索引排序），沿着主轴移动的线程不是合并的。

And to really make this visual—actually, I like this diagram on the right. Imagine I have this 4 by 4 matrix. This is row major. So it's sorted in the order of the yellow block comes first, the red block comes next, and so on and so forth. This is the linear ordering in memory address. This is the matrix that I'm trying to store. Now, imagine that I have threads that are trying to read each column, each clock cycle. So I read a column, I move to the right, I read a column, I move to the right. If I'm doing that at the very first iteration, I hit this element, this element, this element, this element. Notice that each one of these limits a different burst window. And I've read the entire matrix, so to speak, even though all I wanted was a single column. Now, imagine if I was reversed, if I was flipping this matrix, I could read the entire block. Every thread would get its read in a single read of the memory. So coalescing can give you significant improvements in reads from large, contiguous structures like matrices. So this is one reason why you might want to think a little bit about row versus column versus other kinds of ordering.

为了更直观——我其实喜欢右边这张图。想象一个 4x4 矩阵，行主序的。所以按黄色块先、红色块次之等顺序排列。这是内存地址中的线性排列，即我要存储的矩阵。现在想象我有线程，每个时钟周期试图读取每一列。我读一列，右移，再读一列，再右移。在第一次迭代中，我命中这个元素、这个元素、这个元素、这个元素。注意每一个都限制了不同的 burst 窗口。虽然我只要一列，但读出了整个矩阵。如果是反过来，翻转这个矩阵，我就可以读取整个块——每个线程在单次内存读取中获得其数据。所以内存合并可以在从像矩阵这样的大连续结构中读取时，提供显著的改进。这就是为什么你可能需要思考行序 vs 列序 vs 其他排序方式的原因之一。

### Trick 6: Tiling / 技巧六：分块

The last one that I want to talk about—and this is the big one and maybe the most important idea, I've saved it for last—is the idea of tiling. And I think this one has probably the big impact on performance. Tiling, I think, more than any other idea, is this idea of trying to do as much as you can with the memory hierarchy. So what we want to do is, we want to group our memory accesses as much as possible. And shared memory accesses should be done together, and they should be done on shared memory. So the reason why it's called tiling is I'm going to cut up the things that I need. I'm going to tile my space. And each tile will be loaded into my shared memory. And once that tile is loaded, I'm going to repeatedly read from that tile and do as much as I can.

最后一个想讨论的——也是最大的、也许是最重要的想法，我留到了最后——是分块（tiling）的概念。我认为这可能对性能有最大的影响。分块，超越任何其他想法，是关于在内存层级结构中尽可能多做工作的理念。我们想要尽可能多地对内存访问进行分组。共享内存访问应该一起进行，在共享内存上完成。之所以叫分块，是因为我要把需要的东西切割开，像铺瓷砖一样划分空间。每一块（tile）会被加载到共享内存。一旦那块被加载，我会反复从中读取并尽可能多地进行计算。

So let's think about the matrix multiply case. I want to multiply this matrix and this matrix. And this matrix on the right bottom, this is my output. This is where I'm writing my matrix out. Now, if I want to do this, I'm going to be reading through the threads multiple—sorry. The same entry will be read multiple times. And to be precise, each entry will be read n times in an N by N matrix multiply, naively. So you might think, if I'm reading this entry, let's say, multiple times, instead of hitting global memory each time, why can't I group all of those memory accesses together? And the nice thing about matrices is that there's a very natural grouping. And this is to essentially cut the matrix up into submatrices and then load them and then operate upon them.

让我们思考矩阵乘法的场景。我想乘这个矩阵和那个矩阵。右下角的矩阵是输出，是我输出矩阵的地方。如果我想这样做，同一个条目会被多次读取。准确地说，在一个 N×N 的矩阵乘法中，每个条目会被读 N 次。你可能会想，如果这个条目被多次读取，与其每次都访问全局内存，为什么不把所有那些内存访问分组在一起？矩阵的优点是有一个非常自然的分组方式：本质上是把矩阵切成子矩阵，然后加载它们，再操作它们。

So here is a very simple algorithm. I'm going to cut out my matrices into 2 by 2 submatrices. And then I'm going to load different tiles. So I'm going to first load the M 0,0 tile, the top left here. I'm going to load the N 0,0 tile, the top left of my top matrix. And I'm going to load those into shared memory. So I'm going to pay the cost of transferring those slowly from global memory once. But once they're in shared memory, I can read and write very fast with those tiles. This output tile will also be, for now, in shared memory. And I will operate on these submatrices entirely. So I'll multiply these two submatrices. And I'll put the partial sum into my output submatrix. So that allows me to do a bunch of reads and writes all in the shared fast memory. And then I can write it back out when I'm done.

这是一个非常简单的算法。我把矩阵切成 2×2 子矩阵，然后加载不同的块。先加载 M(0,0) 块（左上角），加载 N(0,0) 块（顶部矩阵的左上角），把它们加载到共享内存。我一次性付出从全局内存缓慢传输这些数据的代价。但一旦它们在共享内存中，我就可以非常快速地读写这些块。输出块暂时也在共享内存中。我完全在这些子矩阵上操作：乘这两个子矩阵，把部分和放到输出子矩阵中。这使我能全部在快速的共享内存中进行一批读写操作。完成后我再写回去。

What does the math look like? Well, in the nontiled case, I already told you, each element of my input is going to have to be read n times when I do this big N by N matrix multiply. If I tile them with a tile size of T, then each input is going to be read N over T times from global memory and then T times within each tile. And this makes sense, the extreme. If T is equal to N, I read it once from global memory and access it N times in shared memory. And this is great because the T times reduction in global memory access. If you have big, big shared memory tiles, it means that you can dramatically reduce your global memory access on something like a matmul.

数学上怎样呢？在无分块的情况下，我已经说过，做 N×N 矩阵乘法时，每个输入元素需要被读取 N 次。如果以块大小 T 进行分块，每个输入将从全局内存读取 N/T 次，然后在每个块内访问 T 次。这很有道理，极端情况：如果 T = N，我从全局内存读取一次，在共享内存中访问 N 次。这很棒，因为全局内存访问减少了 T 倍。如果共享内存块非常大，你可以显著减少像矩阵乘法这样操作中的全局内存访问。

So tiling is very, very powerful as an idea, but it's also complex. You can actually end up with some really subtle things happening with tiles. So imagine I have a tile size of 128, 128. If my matrices are 256 by 256, life is good. I've got four tiles, perfectly cut. Now, imagine I increase my coordinate size by one. Now, I've generated two very skinny tiles with basically nothing inside of them. So now you realize, actually, this tile sizing thing is actually pretty complex. Depending on my matrices, I might need to adjust my tile sizes to somehow trade off my memory bandwidth versus this gigantic empty space where I'm doing nothing. The tile sizes is actually a thing that you optimize.

所以分块作为一个概念非常非常强大，但也很复杂。你实际上可能遇到一些非常微妙的事情。假设块大小是 128×128。如果我的矩阵是 256×256，很好，四块完美切割。现在，想象我把坐标大小增加 1。现在生成两个非常窄的块，里面基本上什么都没有。所以你意识到，块大小的选择实际上相当复杂。取决于矩阵大小，我可能需要调整块大小，以某种方式在内存带宽和巨大的空操作空间之间做权衡。块大小实际上是可优化的东西。

So coalesced memory accesses, the size of your shared memory in your accelerator, and the sizes of your matrices all affect which tiles are optimal. And if you know about different options in PyTorch, there's a compiler option called max-autotune. I don't know how many of you have used this or heard about this. You turn on that flag. For the next 15 minutes, PyTorch is going to run an endless series of benchmarking tests. And you'll realize, actually, what it's doing is, it's trying all sorts of different tile sizes on your matrices and trying to figure out which one is actually faster. And you'll find that you'll get nontrivial benefits from actually optimizing these things.

内存合并访问、加速器中共享内存的大小、以及矩阵大小，都影响哪些块大小是最优的。如果你了解 PyTorch 中的各种选项，有一个编译器选项叫 max-autotune。我不知道你们中有多少人用过或听说过这个。你打开那个标志，在接下来的 15 分钟里，PyTorch 会运行一系列无尽的基准测试。你会发现它实际上是在你的矩阵上尝试各种不同的块大小，试图找出哪个实际上更快。你会发现从这些优化中你能获得不小的收益。

The other thing that you'll find related to coalescing is, if your matrices are the wrong size, what you can do is that your attempt to read a tile might actually trigger a lot of memory reads. So imagine I have this nice world where I have this tile and my burst sections are the width of the tile. In this case, if I do four reads, I'm good to go. Because of the burst sections, I read this entire submatrix, so good memory reads from coalescing. Now, imagine I shift the matrix size by one. Now I've bumped this first row over. So this blue box now lives over here. And there's no way for me to coalesce my reads to read a single tile in one go because now all these things are ragged and misaligned. So I need to do at least two tiles worth of reads to read out this one tile. So there's actually a lot of complexities involved in optimizing tile reads once you start thinking about coalescing and all these other things. And so in this case, what you have to do is padding in order to line up, essentially, the boundaries of the burst sections with the tile sizes that you have.

与合并相关的另一个发现是：如果你的矩阵大小不对，尝试读取一个块实际上可能触发大量内存读取。想象一个美好的世界：我的 burst 段宽度正好是块的宽度。在这种情况下，四次读取就够了——由于 burst 段，我读取整个子矩阵，从合并中获得了良好的内存读取。现在，想象我把矩阵大小改变 1。第一行被推后了。所以这个蓝色框现在跑到这里了。我没有办法在一次合并读取中读取单个块，因为现在所有东西都是参差不齐、不对齐的。所以我需要至少做两次块的读取量来读出这单个块。所以一旦你开始考虑合并和所有这些其他因素，优化块读取实际上有相当多的复杂性。因此你不得不做 padding 来对齐 burst 段的边界和你拥有的块大小。

And this is why you end up getting stuff like this, which seems very mysterious. I think this is one of my favorite weird ones. Andrej Karpathy, when he was doing nanoGPT speedruns, said well, when I increase my vocab size from 50,257 to 50,304, I got a 25% speedup. And it's kind of weird to have to pad in order to get a speedup. But maybe it makes sense once you realize things like this. Padding can start to shift the rows and columns so that you actually get very efficient reads, whereas at other times, you do not.

这就是为什么你会得到这样的现象，看起来非常神秘。我想这是我最喜欢的奇怪事例之一。Andrej Karpathy 在做 nanoGPT 加速挑战时说：当我把词汇量从 50,257 增加到 50,304 时，获得了 25% 的加速。必须通过 padding 来获得加速有点奇怪。但一旦你意识到这样的事情，也许就有道理了：padding 可以改变行和列的排列，使你的读取非常高效，而在其他时候则不然。

The thing that is tricky about FlashAttention, and you'll see this in the assignment, is there's a big global softmax on the whole thing. Normally, to compute a softmax, you would do it this way: you would exponentiate all of your elements. You would subtract the maximum for numerical stability reasons. FlashAttention 的难点，你会在作业中看到，是有一个全局 softmax 贯穿整个计算。所以我们不能直接朴素地做，因为 softmax 是一个全局操作，把所有的东西都连在一起——它把所有不同的块连接起来。如何对注意力进行分块可能不是那么显然。关键的技巧——一旦你看到它，这真的是核心思想或观察——一旦你看到这个，剩下的就很简单了。通常计算 softmax 的方式是：对所有元素取指数，减去最大值（为了数值稳定性），然后归一化——标准的 softmax。现在有一种在线计算的不同方式。一旦你意识到这一点，其实很简单：你在进行过程中逐步计算归一化的 softmax。每当你遇到比之前见过的更大的数时，你就替换掉最大值。这样你就有了一种在线计算 softmax 的方法。唯一棘手的当然是最大值，而我们处理最大值的方式是：追踪最大值，每当我们看到一个新的最大值时就替换并修正。除此之外，这实际上不过是一个在线的指数运行和。当然，在最后，你将一切除以你在在线计算中得到的累加器。
